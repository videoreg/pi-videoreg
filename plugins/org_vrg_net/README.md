# Network plugin (org_vrg_net)

WiFi (client / access point), modem connection, WireGuard. Runs inside `vrg-core`.

This document currently covers WireGuard only.

## WireGuard

### Overview

The tunnel is used for two things:

- **Reaching the device**: web UI, ssh, RTSP from the VPN side. This always works while the
  tunnel is up.
- **Outbound traffic of selected plugins**, e.g. Telegram through the VPN while VK goes
  directly. Nothing is routed through the tunnel by default: even with WireGuard up, all
  outbound traffic uses the main connection (WiFi or modem).

Unlike a plain `wg-quick up`, the tunnel **never becomes the device's default route**, even
when the peer has `AllowedIPs = 0.0.0.0/0`.

### Bringing the interface up and down

| Who | What |
|-----|------|
| Monitor loop (`prod/wg.py`, every 10 s) | Runs while "Auto-connect" is on (`wg_auto`, default on). Brings the tunnel down while the `vrg-wifi` client connection is active if "Don't connect for WiFi Client" is on (`wg_skip_on_wifi`, default on). Otherwise brings it up |
| "State" switch in the UI (`net.wg_set_state`), `/wg_on` and `/wg_off` bot commands | Bring it up or down right now and save nothing. With auto-connect on, the monitor may undo this on its next pass |
| Saving the config (`net.save_wireguard_config`) | Restarts the tunnel if it is up, so the new config applies at once |

All of them run `sudo wg-quick up|down wg0` under one lock in the monitor, so they never race.

### Config file

`/etc/wireguard/wg0.conf` is generated by net (`wg_config.py`) from the fields of the form in
Settings → WireGuard. It is never edited as text, so the lines videoreg relies on are always
there:

```
# Generated by videoreg (Settings -> WireGuard). Manual edits are lost on the next save.
[Interface]
PrivateKey = ...
Address = 192.168.87.9/24
MTU = 1380                     # only if set
Table = off                    # wg-quick installs no routes
PostUp = bash <project>/task/net/wg-routes.sh up %i
PreDown = bash <project>/task/net/wg-routes.sh down %i

[Peer]
PublicKey = ...
PresharedKey = ...             # only if set
Endpoint = vpn.example.com:51820
AllowedIPs = 192.168.87.0/24, 0.0.0.0/0
PersistentKeepalive = 25       # only if set
```

| Form field | Key | Validation |
|------------|-----|------------|
| Private key | `PrivateKey` | WireGuard key (base64, 32 bytes). Empty on save keeps the current one |
| Address | `Address` | Comma-separated `ip/prefix` list |
| MTU | `MTU` | Optional, 576–9000 |
| Server address | `Endpoint` | `host:port` or `[ipv6]:port` |
| Server public key | `PublicKey` | WireGuard key |
| AllowedIPs | `AllowedIPs` | Comma-separated networks, normalized (`192.168.87.9/24` → `192.168.87.0/24`) |
| Keepalive | `PersistentKeepalive` | Optional, 0–65535. The form suggests 25 for a new config |
| Preshared key | `PresharedKey` | Optional WireGuard key |

There is a single peer, the VPN server. What the form does not offer is not supported:

- `DNS`, because the system resolver must not depend on the tunnel being up;
- `ListenPort`, which a client does not need;
- custom hooks and other peers.

Validation is strict because the values go into a file that wg-quick runs as root. For
example, a newline in a field must not be able to add a `PostUp` line.

The file itself is the only storage: to fill the form, net parses the file back
(`parse_config`). The private key is never sent to the browser. The client gets
`has_private_key` and the derived public key (`wg pubkey`), which is shown with a copy button,
because that is the key to register on the server.

On save (`save_wireguard_config`):

1. An empty private key is replaced with the current one.
2. The fields are validated and normalized (`normalize_settings`). An invalid field gives the
   error "Invalid value: <field>".
3. The previous file is kept as `wg0.conf.backup`. The new one is written with mode 600.
4. If the tunnel is up, it is restarted (`restart_wireguard()`). Connections through the tunnel,
   including the web UI session if it goes through WireGuard, drop for a few seconds.

**Import .conf** (`import_wireguard_config`) parses a pasted client config, e.g. one exported
by a VPN server panel, into the form fields. It saves nothing. Unsupported lines (DNS,
ListenPort, hooks, extra peers) are returned as `ignored` and shown in the form as a warning.

The hook path in the file is absolute (the project directory). If the project moves, open the
form and save it again.

### Routing (`task/net/wg-routes.sh`)

wg-quick runs the script as root, so it needs no sudoers entry of its own. On `up`:

1. Every AllowedIPs prefix except the default one goes into the **main** table
   (`ip route replace <prefix> dev wg0`). The VPN subnet and networks behind the peer stay
   reachable for everyone.
2. Every AllowedIPs prefix, including `0.0.0.0/0` → `default dev wg0`, goes into table
   **51821**.
3. For every address of the interface, a rule `from <wg address> lookup 51821` is added at
   priority 1000.

On `down`, all rules pointing to table 51821 are deleted and the table is flushed. `up` starts
with the same cleanup, so running it twice is harmless. The script always exits 0, so a
routing failure never tears the interface down.

Example with `Address = 10.8.0.2/24` and `AllowedIPs = 10.8.0.0/24, 0.0.0.0/0`:

```
$ ip rule
0:      from all lookup local
1000:   from 10.8.0.2 lookup 51821
32766:  from all lookup main

$ ip route show table 51821
default dev wg0 scope link
10.8.0.0/24 dev wg0 scope link

$ ip route get 149.154.167.220                  # ordinary socket
149.154.167.220 via 192.168.1.1 dev wlan0 src 192.168.1.50
$ ip route get 149.154.167.220 from 10.8.0.2    # socket bound to the tunnel address
149.154.167.220 from 10.8.0.2 dev wg0 table 51821
```

What goes through the tunnel is decided by the packet's **source address**, not its
destination:

- **Inbound connections** (web UI, ssh). A peer connects to `10.8.0.2`, and the kernel answers
  from that address. The reply matches the rule and goes back through wg0, wherever the client
  is. This includes networks routed by the VPN server, e.g. the user's home LAN. Nothing
  special is needed in `org_vrg_http` or sshd.
- **Outbound connections of selected plugins.** The plugin binds its socket to `10.8.0.2`
  (see below), so the connection matches the same rule.
- **Everything else** uses unbound sockets and follows the main table, i.e. the main
  connection.
- **The encrypted UDP traffic of WireGuard itself** uses an unbound socket too, so it always
  goes over the main connection.

The table number appears in two places that must stay in sync: `TABLE` in `wg-routes.sh` and
`WG_ROUTE_TABLE` in `const.py`.

### Per-plugin outbound routing

The selection is stored in the plugin state under `wg_egress_plugins`: a list of plugin ids,
empty by default. It is edited on the **Settings → WireGuard → Routing** tab.

A plugin is listed there if its `manifest.yaml` declares:

```yaml
net:
  egress:
    title: $bot.telegram.menu   # i18n key with "$", or plain text
```

The plugin must also create its outbound connections through `sdk/egress.py`:

```python
# plugin_builder.py
plugin.init_api_client()
plugin.init_egress()

# making a request: a new session per request picks up route changes
async with aiohttp.ClientSession(connector=await plugin.egress.connector()) as session:
  ...
```

How a connection gets its route:

1. `Egress.local_address()` calls `net.wg_egress {"plugin": <id>}` and caches the answer for
   10 s. A change in the UI therefore applies to new connections within about 10 s, with no
   restart.
2. `net.wg_egress` returns the tunnel's IPv4 address only if all of these hold, and `None`
   otherwise:
   - the plugin is selected;
   - wg0 has an IPv4 address;
   - the `from <address>` rule exists;
   - table 51821 has a default route, i.e. the peer's AllowedIPs include `0.0.0.0/0`.

   The answer for a plugin that is not selected comes from the state alone, with no
   subprocesses. For a selected plugin, the kernel state is read with `ip` (three calls) and
   cached in the monitor for up to 60 s. The cache is dropped whenever the monitor brings the
   interface up or down, or notices that someone else did.
3. `Egress.connector()` returns `TCPConnector(local_addr=(address, 0), family=AF_INET)` when
   there is an address, or a plain `TCPConnector()` otherwise.

The plugin falls back to the main connection (fail-open) when the tunnel is down, when it
cannot reach the internet, and when `net` is unavailable.

Limitations:

- **IPv4 only.** A WireGuard-routed plugin connects over IPv4 even if the host also has IPv6.
- **DNS** for these plugins is still resolved through the main connection.
- **Tunnel up but dead.** If there is no handshake, connections bound to the tunnel time out.
  There is no fallback for this yet.
- **Traffic of subprocesses** (curl, ffmpeg, ...) is not covered. Only connections made via
  `Egress` follow the setting.

Current users: `org_vrg_bot` (`telegram_api.py`) and `org_vrg_botvk` (`vk_api.py`). Both
create sessions through their `_session()` helper.

### API

| Method | HTTP | Purpose |
|--------|------|---------|
| `wg_show` | `GET /api/net/wireguard_status` | Interface state, address, peers (`wg show`) |
| `wg_settings` | `GET /api/net/wireguard_settings` | `active`, `auto`, `skip_on_wifi` |
| `wg_set_state` | `POST /api/net/wireguard_state` | `{"enabled": bool}`: bring the tunnel up or down now |
| `wg_auto` | `POST /api/net/wireguard_auto` | `{"enabled": bool}`: auto-connect (monitor loop) |
| `wg_skip_on_wifi` | `POST /api/net/wireguard_skip_on_wifi` | `{"enabled": bool}` |
| `get_wireguard_config` | `GET /api/net/wireguard_config` | Form fields parsed from `wg0.conf`, `has_private_key`, `public_key` (no private key) |
| `save_wireguard_config` | `POST /api/net/wireguard_config` | `{"settings": {...}}`: validate, generate `wg0.conf`, restart the tunnel if it is up. Returns `{"active", "restarted"}` |
| `import_wireguard_config` | `POST /api/net/wireguard_config_import` | `{"content": str}` → `{"settings", "public_key", "ignored"}`. Saves nothing |
| `generate_wireguard_key` | `POST /api/net/generate_wireguard_key` | New key pair |
| `wg_routing` | `GET /api/net/wireguard_routing` | Plugins that can be routed with their `via_wg` flag, plus `active`, `address`, `routing` (rule present), `default_route` |
| `wg_set_routing` | `POST /api/net/wireguard_routing` | `{"plugin": <id>, "via_wg": bool}` |
| `wg_egress` | — (internal, used by `sdk/egress.py`) | `{"plugin": <id>}` → `{"address": str or None}` |

### Troubleshooting

```bash
ip rule                                  # is there "from <wg address> lookup 51821"?
ip route show table 51821                # is there "default dev wg0"?
ip route get 1.1.1.1 from <wg address>   # must say "dev wg0"
sudo cat /etc/wireguard/wg0.conf         # Table = off and the wg-routes.sh hooks present?
vrg-log net -f                           # "Starting WireGuard...", wg-quick errors
vrg-log bot | grep egress                # "egress: outbound traffic via WireGuard (...)"
```

If the Routing tab says the routing is not set up, turn WireGuard off and on again. That
reruns the hook. If `wg0.conf` has no `Table = off` or no hooks, it was not written by the
form: save the form once.
